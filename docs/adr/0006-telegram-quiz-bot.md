# ADR-0006: Telegram quiz bot runs grammY over long polling, bundled with esbuild

- Status: accepted
- Date: 2026-10-07
- Area: `src/features/telegram-quiz`

## Context

Day 27 integrates the local MLX model (Day 26) into a real application. The task allows a CLI, a bot or
a web app; the existing `/local-llm` page already covers the web case, so the deliverable is a Telegram
quiz bot: MC questions generated by the local model, answered with inline buttons.

The repo keeps the LLM transport on raw `fetch` and treats every non-LLM SDK as a deliberate decision.
A Telegram bot could talk to the Bot API with raw `fetch` and a hand-rolled `getUpdates` loop, or use a
framework. It also needs a way to run TypeScript as a standalone process outside the TanStack Start
build, which already has a precedent: MCP servers ship as esbuild-bundled `.mjs` (`npm run build:mcp`).

## Decision

- **Transport:** grammY (`grammy`) with **long polling** (`bot.start()`), a deliberate non-LLM SDK
  exception. Long polling needs no public URL/webhook and processes updates sequentially, so per-chat
  round state cannot race. The bot reaches the local model through the shared `callCompletions` (via
  `@lib/local-llm.server`), never the other way around; grammY never touches the browser or the LLM
  transport.
- **Question novelty and validity:** the prompt does **not** list the already-asked questions. At low
  temperature that negative list makes the model echo the forbidden question (observed live: the same
  stem four times, with a different "correct" answer each time). Diversity comes from a higher generation
  temperature plus a normalized duplicate check in the generator, which regenerates on a repeat. The
  schema also rejects an MC whose four options are not distinct after normalization — an 8B model emits
  degenerate questions where every option is the same string (observed: all four options
  "Сверхъестественное"), which would otherwise make every tap "correct" — and rejects text outside
  Cyrillic/Latin (both models leak Han characters into Russian names, e.g. `Дэвид芬奇`). The generator fails the round if
  every attempt is invalid. The quiz model is configurable via `QUIZ_LLM_MODEL` (fallback
  `LOCAL_LLM_MODEL`), so a larger local model can be used for the quiz alone.
- **Packaging:** `scripts/build-bot.mjs` bundles `bot/entry.ts` into `dist/server/bot/telegram-quiz.mjs`
  with `packages: 'external'` (like MCP); `npm run bot` builds and runs it. `grammy` stays external.
- **State:** an in-memory `RoundStore` (`Map<chatId, RoundState>` with lazy TTL purge), not
  `@grammyjs/sessions`. The quiz state is a per-chat round with its own lifecycle, and a plain store
  keeps the domain free of the framework and testable without grammY.
- **No streaming:** a question is a JSON object, so it must be complete before the buttons render;
  Telegram also throttles message edits. Generation shows a `typing` action instead.
- **Shared local config:** endpoint resolution and the `/models` health check are extracted to
  `@lib/local-llm.server` (`runLocalChat`, `getLocalLlmStatus`), so both `features/local-llm` and
  `features/telegram-quiz` use one source instead of importing each other.

## Consequences

- One new runtime dependency, `grammy`, confined to `features/telegram-quiz`.
- Offline tests drive the bot via `bot.handleUpdate` with a mocked API transformer and an injected
  `QuestionGenerator`/`RoundStore`; no network or bot token needed.
- Only `api.telegram.org` is contacted at runtime — the model itself stays local, and a dead MLX server
  degrades softly with a hint instead of crashing the round.
- The bot is dev/local-only, like the local model it depends on; it is not part of `vite build`.
