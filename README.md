# AI Advent Challenge

### Запуск

```bash
npm install
cp .env.example .env   # впиши DEEPSEEK_API_KEY
npm run dev            # http://localhost:3000
```

### Env

| Переменная           | Обязательна | Описание                                      |
| -------------------- | ----------- | --------------------------------------------- |
| `DEEPSEEK_API_KEY`   | да          | Ключ API DeepSeek                             |
| `DEEPSEEK_MODEL`     | нет         | Модель (по умолчанию `deepseek-flash`)        |
| `HUGGING_FACE_TOKEN` | для Day 5   | Ключ Hugging Face (слабая модель через роутер) |

`.env` в gitignore — ключ никогда не коммитится. Полный список переменных — в `.env.example`.

## Day 1 — минимальный вызов LLM

Страница `/day1`: запрос в DeepSeek через OpenAI-совместимый `chat/completions`; ключ и модель читаются из `process.env` на сервере и не попадают в браузер.

## Day 2 — формат ответа

Страница `/day2`: один промпт в двух вкладках — свободная форма и жёсткий JSON-контракт (`response_format: json_object`), с инспектором отправленного запроса.

## Day 3 — стратегии промпта

Страница `/day3`: одно задание решается четырьмя способами (direct, step-by-step, prompt-crafted, expert panel), ответы сравнивает LLM-судья с эталоном.

## Day 4 — температура

Страница `/day4`: один запрос трижды с `temperature` 0 / 0.7 / 1.2, сравнение точности и креативности.

## Day 5 — версии моделей

Страница `/day5`: одно ТЗ уходит в три модели разного уровня (HF-роутер, `deepseek-flash`, `deepseek-v4-pro`); на карточках — ответ, время и токены.

## Day 6 — первый агент

Агент как отдельная сущность: `input policy → decide → act → finalize → судьи`; права из мок-токена, инструменты брони и отпусков, судьи проверяют ответ и бизнес-правила.

## Day 7 — сохранение контекста

`/agent` получает память: история и бизнес-факты переживают перезапуск; хранилище — SQLite (`node:sqlite`), несколько сессий на персону.

## Day 8 — работа с токенами

Агент считает и контролирует токены: оценка запроса/истории, реальный `usage` API, цена за ход, бюджет контекста и отклонение слишком больших запросов.

## Day 9 — сжатие истории

Последние сообщения идут как есть, старый диалог сворачивается в сводку и подставляется отдельным `system`-блоком; сводка хранится в БД, есть A/B «со сжатием / без».

## Day 10 — стратегии контекста

Единый роут `/agent` (старые `/agent-*` редиректят): контекст собирается одной из стратегий на сессию — скользящее окно, key-value факты или ветки диалога.

## Day 11 — память агента

В «Настройках» `/agent` — явная модель памяти из трёх раздельно хранимых слоёв: short-term (диалог), working (данные задачи), long-term (профиль и решения); `MemoryRouter` решает, что куда писать.

## Day 12 — профиль пользователя

В «Настройках» `/agent` — структурированный профиль (обращение, тон, язык, длина, формат, ограничения), хранится по `token`, фиксируется за сессией и подставляется в каждый запрос; есть профиль по умолчанию.

## Day 13 — состояние задачи

Намерение пользователя — конечный автомат `planning → execution → validation → done` (+ `paused`/`cancelled`); этап и шаг переживают ходы, состояние видно в строке задачи и истории.

## Day 14 — инварианты и инструменты

Глобальные правила применяются ко всем сессиям: пять закреплённых проверок, при нарушении действие/ответ блокируется с кодом `INV-*`; правила редактируются во вкладке «Инварианты», закреплённые неизменяемы.

## Day 15 — управляемые переходы задачи

Переходы между этапами идут через один reducer и граф допустимых переходов; недопустимый переход отклоняется и виден в ленте, `planning → execution` требует согласия, после мутации задача сама уходит на проверку.

## Day 16 — подключение MCP

Локальный MCP-сервер на `@modelcontextprotocol/sdk` отдаёт демо-инструменты `now` и `echo`; серверный клиент поднимает stdio-процесс и читает `tools/list`, список виден во вкладке «MCP». SDK живёт только на сервере.

## Day 17 — инструменты БД и MCP в агенте

MCP-сервер получает read-only инструменты базы (`db_overview`, `bookings_by_room`, `employee_schedule`); агент видит их как обычные инструменты (с префиксом `mcp_`) и отвечает по их результатам.

## Day 18 — планировщик погоды поверх MCP

Второй сервер `agent-mcp-jobs` со своей `jobs.sqlite`: расписания погоды, сводки и точечные запросы, скрытый тик `run_due_jobs` (дёргается таймером через `GET /jobs/tick`); данные — Open-Meteo без ключа.

## Day 19 — пайплайн MCP-инструментов

Третий сервер `agent-mcp-research` пишет отчёты: `search` → `summarize` → `save_to_file` плюс проверочные `list_reports`/`read_report`. Цепочку ведёт обычный цикл агента (вывод предыдущего инструмента в аргументы следующего), отдельного движка пайплайна нет.

## Day 20 — оркестрация нескольких MCP-серверов

Четвёртый сервер `agent-mcp-market` (`exchange_rate`, данные ЕЦБ без ключа). Агент комбинирует инструменты нескольких серверов в одном ходу (длинный флоу из четырёх серверов, до 10 действий), порядок вызовов задают описания.

## Day 21 — индексация документов (RAG)

Фича `/rag`: корпус из 15 статей Википедии о городах России, две стратегии чанкинга (по токенам и по структуре), локальные ONNX-эмбеддинги (`Xenova/multilingual-e5-base`), индекс в `rag.sqlite`, поиск косинусом. «Сравнение» считает `recall@3/@5`/`MRR`. Механика — в `src/features/rag/README.md`.

## Day 22 — первый RAG-запрос

Вкладка «Ответ»: вопрос уходит в LLM **с RAG** (top-k чанков → контекст → ответ со ссылками `[n]`) и **без RAG** — рядом. «Контроль» прогоняет 10 контрольных вопросов и строит scorecard.

## Day 23 — реранкинг, порог и query rewrite

Второй этап после поиска: cross-encoder (`Xenova/bge-reranker-base`, fail-open) переоценивает пары и порог отсекает нерелевантное, плюс опциональный query rewrite. Режимы: `rag`, `rag+rerank`, `rag+rewrite`, `rag+rewrite+rerank`.

## Day 24 — контракт ответа и «не знаю»

Ответ RAG стал контрактным: строгий JSON с цитатами, сервер добавляет источники и проверяет дословность цитат (`ungrounded`); ниже порога — abstain «не знаю» без вызова LLM. Решение — в `docs/adr/0005-rag-answer-contract-and-abstention.md`.

## Day 25 — RAG как способность агента

RAG становится способностью `/agent`: при `ragEnabled` поиск идёт на каждом Ходу, источники показываются всегда, плюс read-only инструмент `rag_search`. `features/agent` **не импортирует** `features/rag` — их связывает `src/lib/agent-rag.server.ts` через шов `AgentCapability`; память задачи живёт в рабочей памяти агента.

## Day 26 — запуск локальной LLM

Страница `/local-llm`: **Qwen3-8B-4bit** локально на Apple Silicon через MLX (`mlx_lm.server`), OpenAI-совместимый API без облака и ключа; три пресета + свободный ввод, метрики латентности и токенов. Эндпоинт — `LOCAL_LLM_BASE_URL`/`LOCAL_LLM_MODEL`; выключенный сервер даёт мягкую деградацию. Dev-сценарий.

## Day 27 — телеграм-квиз на локальной LLM

Отдельный бот `features/telegram-quiz` (grammY + long polling) генерирует вопросы викторины локальной моделью и отдаёт инлайн-кнопками. Запуск — `npm run bot`, токен — `TELEGRAM_BOT_TOKEN`, модель — `QUIZ_LLM_MODEL`; наружу ходит только `api.telegram.org`. Решения — в `docs/adr/0006-telegram-quiz-bot.md`.

## Day 28 — локальная LLM в RAG-пайплайне

У RAG-ответа появился выбираемый `generator` (`cloud` | `local`, по умолчанию `cloud`); локальный адаптер ходит в **Qwen3-14B-4bit** через `@lib/local-llm.server` (`RAG_LLM_MODEL`), контракт, цитаты и abstain те же, что у облака. «Контроль» сравнивает оба генератора по качеству, скорости и стабильности. Детали — в `src/features/rag/README.md`.

## Day 29 — оптимизация локальной LLM

Вкладка `/llm-opt` — OFAT-стенд под извлечение факта (город → JSON): перебор prompt/параметров/контекста и сравнение квантизаций по качеству, скорости и памяти. Итог: качество решает prompt-схема, а не параметры; из квантизаций для этой задачи выгоднее 8B-4bit. Запуск и таблица — в `src/features/llm-opt/README.md`.

## Day 30 — локальная LLM как приватный сервис

`features/llm-service` — приватный сервис над локальной моделью: OpenAI-совместимый HTTP API и чат-страница, с ключами доступа, rate limit, ограничением контекста и стримингом SSE. Mac — «домашний сервер», шлюз публикуется через Tailscale Funnel и держится `launchd`. Запуск — `npm run llm-service`, проверка лимитов — `npm run llm-service:load`. Детали — в `src/features/llm-service/README.md` и `docs/adr/0008-local-llm-as-public-service.md`.

## Day 31 — ассистент разработчика

Страница `/dev-assistant` — чат, который отвечает **о самом проекте**: корпус из доков, README всех фич, ADR и схем данных читается с диска и индексируется отдельным SQLite; состояние репозитория (ветка, коммиты, дифф) приходит из собственного read-only git-MCP-сервера; `/help` показывает карту проекта. Общие швы вынесены в `src/lib` (`rag-engine.server.ts`, `mcp/`). Детали — в `src/features/dev-assistant/README.md`, решения — в `docs/adr/0009-shared-rag-engine-and-dev-assistant.md`, `docs/adr/0010-mcp-host-in-lib.md` и `docs/adr/0011-day31-architecture-refactor.md`.

## Day 32 — автоматическое ревью pull request

Тот же движок как headless-пайплайн: GitHub Action (`.github/workflows/pr-review.yml`) запускает `features/dev-assistant/cli/review.ts` на PR и вручную по номеру, берёт дифф из `git diff base...head`, строит индекс из доков **и кода** проекта под стратегией `review` и просит модель вернуть `{summary, findings}`; второй этап — судья, который оставляет только подтверждённые фактами находки (`PR_REVIEW_JUDGE=0` выключает его). Валидные находки становятся inline-комментариями, остальное собирается в один стики-комментарий; сбой деградирует в пометку и не блокирует PR. Детали — в `src/features/dev-assistant/README.md`, решения — в `docs/adr/0012-pr-review-pipeline.md` и `docs/adr/0013-review-judge-stage.md`.

## Day 34 — ассистент для работы с файлами проекта

`/dev-assistant` работает и с файлами: вопросы по докам идут прежним RAG-путём, «найди/прочитай» — read-only циклом, а правки оформляются планом и после подтверждения проходят `execution → validation → done` с проверкой чтением и diff. Инструменты даёт MCP-сервер `dev-assistant-mcp-files` в песочнице с защищёнными путями; изменения ограничены pinned-инвариантами (только файлы из плана, без секретов и защищённых путей). Движок цикла, FSM задач и инварианты вынесены в `src/lib` и переиспользуются агентом; цели «подготовь diff» и «проверь инварианты» отвечают детерминированно. Детали — в `src/features/dev-assistant/README.md`, решения — в `docs/adr/0014-agent-loop-task-state-invariants-in-lib.md` и `docs/adr/0015-day34-architecture-refactor.md`.

## Day 35 — авторевью студенческого проекта

`/auto-review` — консоль проверяющего: архив или папка с проектом «Шесть городов», подтверждение плана и отчёт по критериям. Вердикты детерминированы: Б1/Б2/Б3 — Playwright в Chromium и Firefox (необработанные ошибки консоли, сетевые не в счёт), семь Д-правил — статически по исходникам, остальные Д — DeepSeek, замечания только по проваленным пунктам. Неработоспособный проект даёт «не проверено» с причиной, но проверки по коду идут. Состояние ведёт `@lib/task-state` (`planning → execution → validation → done`), прогресс — в своём SQLite; прогон можно прервать, повторный — только по проваленным пунктам; отчёт и замечания копируются в Markdown. Детали — в `src/features/auto-review/README.md`, решение — в `docs/adr/0018-day35-auto-review.md`.
