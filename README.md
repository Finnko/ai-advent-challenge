# AI Advent Challenge

Ежедневные шаги по изучению AI. Каждый день — отдельная ветка `feature/dayN`, после проверки
вмерживается в `main`. Дни собраны в общем каркасе приложения; агентские дни развивают единый экран
`/agent`.

**Стек:** TanStack Start (Vite + React 19 + TypeScript), Tailwind v4, голый `fetch` — никаких SDK на LLM-слое.

### Запуск

```bash
npm install
cp .env.example .env   # впиши DEEPSEEK_API_KEY
npm run dev            # http://localhost:3000
```

### Env

| Переменная           | Обязательна | Описание                                     |
| -------------------- | ----------- | -------------------------------------------- |
| `DEEPSEEK_API_KEY`   | да          | Ключ API DeepSeek                            |
| `DEEPSEEK_MODEL`     | нет         | Модель (по умолчанию `deepseek-flash`)       |
| `HUGGING_FACE_TOKEN` | для Day 5   | Ключ Hugging Face (слабая модель через роутер) |

`.env` в gitignore — ключ никогда не коммитится.

## Day 1 — минимальный вызов LLM

Страница `/day1`: запрос в DeepSeek через OpenAI-совместимый `chat/completions`, обычный текстовый
ответ. Ключ и модель читаются из `process.env` на сервере и не попадают в браузер.

## Day 2 — формат ответа

Страница `/day2`: один промпт в двух вкладках — свободная форма и жёсткий JSON-контракт
(`response_format: json_object`), с инспектором отправленного запроса.

## Day 3 — стратегии промпта

Страница `/day3`: одно задание решается четырьмя способами (direct, step-by-step, prompt-crafted,
expert panel), ответы сравнивает отдельный вызов-судья с эталоном.

## Day 4 — температура

Страница `/day4`: один запрос трижды с `temperature` 0 / 0.7 / 1.2, сравнение точности и
креативности. Встроенная задача с эталоном и поле для своего промпта.

## Day 5 — версии моделей

Страница `/day5`: одно ТЗ уходит в три модели разного уровня (HF-роутер, `deepseek-flash`,
`deepseek-v4-pro`); на карточках — ответ, время и токены.

## Day 6 — первый агент

Агент как отдельная сущность: `input policy → decide → act → finalize → судьи`. Права роли берутся
из мок-токена, инструменты — бронь переговорки и отпуска, судьи проверяют ответ и бизнес-правила.

## Day 7 — сохранение контекста

Агент на `/agent` получает память: история и бизнес-факты переживают перезапуск. Хранилище —
SQLite (`node:sqlite`), люди в таблице `people`, несколько сессий на персону.

## Day 8 — работа с токенами

Агент считает и контролирует токены: оценка запроса/истории, реальный `usage` API, цена за ход,
маленький бюджет контекста и отклонение слишком больших запросов.

## Day 9 — управление контекстом: сжатие истории

Последние сообщения уходят как есть, старый диалог сворачивается в сводку и подставляется в промпт
отдельным `system`-блоком. Сводка хранится в БД, кеш-ориентированный промпт, A/B «со сжатием / без».

## Day 10 — стратегии контекста

Единый роут `/agent` (старые `/agent-strategies`, `/agent-memory`, `/agent-profile` редиректят):
контекст собирается одной из стратегий на сессию — скользящее окно,
key-value факты или ветки диалога. Стратегия фиксируется за сессией, есть сравнение по сценарию.

## Day 11 — память агента

Во вкладке «Настройки» единого `/agent` доступна явная модель памяти из трёх слоёв, которые хранятся раздельно.

- **short-term** — текущий диалог (`messages`);
- **working** — данные текущей задачи (`working_memory`, сбрасывается с сессией);
- **long-term** — профиль и решения (`long_term_memory`, переживает сессии).

`MemoryRouter` решает, что и куда сохранять; инспектор показывает содержимое слоёв, есть ручные
записи.

## Day 12 — профиль пользователя

Во вкладке «Настройки» `/agent`: структурированный профиль (как обращаться, тон, язык, длина ответов, формат,
ограничения, свободные инструкции) редактируется в UI и хранится по `token`.

- профиль **фиксируется за сессией** (`sessions.profile_id`) и подставляется в каждый запрос
  автоматически отдельным `system`-блоком; клиент передаёт только id профиля и конфигурацию новой сессии;
- **профиль по умолчанию** применяется к новым сессиям, флаг дефолта один на пользователя;
- профиль по умолчанию используется для новых сессий, а выбор явного профиля задаётся в настройках.

Пример контраста: Анна — формально по-русски, Пётр — дружелюбно по-французски.

## Day 13 — состояние задачи

Намерение пользователя — конечный автомат `planning → execution → validation → done` (плюс `paused`
и `cancelled`). На планировании агент предлагает план и ждёт согласия, на исполнении выполняет
изменяющие действия, на проверке подтверждает результат справочными инструментами.

Этап, шаг и ожидаемое действие переживают ходы: пауза/продолжение не требуют объяснять задачу
заново, а исправление возвращает её на исполнение. Состояние видно в строке задачи и истории чата.

## Day 14 — инварианты и дополнительные инструменты

Глобальные для пользователя правила применяются ко всем сессиям. Пять закреплённых проверяют время
окончания встреч, длительность отпуска, доступность «Ориона», использование SQLite и хранение
секретов на сервере. При нарушении агент блокирует действие или ответ с кодом `INV-*` и предлагает
совместимую альтернативу.

Правила редактируются во вкладке «Инварианты»; закреплённые нельзя удалить, их id и проверка
неизменяемы. Для пользовательских правил без встроенной проверки есть необязательный LLM-guard.
Добавлены `cancelVacation`, `rejectVacation`, `rescheduleBooking`, `getRoomSchedule`, `updateBooking`
и `declineInvite`; результаты проверок хранятся с ходом и показываются бейджами `INV-*`.

## Day 15 — управляемые переходы задачи

Переходы между этапами идут через один reducer и граф допустимых переходов: недопустимый переход
отклоняется, состояние не меняется, а отказ виден в ленте чата. Переход `planning → execution`
невозможен без явного согласия пользователя и закрытого плана. После успешного изменяющего действия
задача сама уходит на проверку, а после реальной справочной проверки — в `done`; сообщение об ошибке
результата детерминированно возвращает её в исполнение.

## Day 16 — подключение MCP

Локальный MCP-сервер (`src/features/agent/mcp/`) на официальном SDK `@modelcontextprotocol/sdk`
(`zod` для схем параметров) отдаёт два демо-инструмента: `now` без параметров и `echo` с входным
параметром `text`.

Серверный клиент (`server/mcp.server.ts`) поднимает stdio-процесс, получает `tools/list` и сразу
закрывает соединение; шов транспорт-нейтральный — позже сюда добавятся `callTool` и удалённый
транспорт. Список доступных инструментов виден во вкладке «MCP» (имя, описание, JSON-схема
параметров) и проверяется офлайн-тестом `tests/mcp.test.ts`. MCP SDK живёт только на сервере и в
браузер не попадает.

## Day 17 — инструменты базы и интеграция MCP с агентом

MCP-сервер получает три инструмента чтения базы агента: `db_overview`, `bookings_by_room` и
`employee_schedule` (база открывается read-only, без миграций). Найденные MCP-инструменты
подключаются к агенту: он видит их как обычные инструменты (с префиксом `mcp_`), выбирает их в
решении и отвечает по их результатам. Они только читают, поэтому доступны на любом этапе задачи.
Во вкладке «MCP» виден список инструментов с параметрами; офлайн-тесты проверяют вызов `now` и
DB-инструментов, а также ход агента с MCP-инструментом.

## Day 18 — планировщик погоды поверх MCP

Второй MCP-сервер `agent-mcp-jobs` со своей базой `jobs.sqlite`: расписания периодического сбора
погоды (`schedule_weather_report`, `cancel_schedule`, `list_schedules`), сводки и точечные запросы
(`get_weather_report`, `get_weather_at`) и системный тик `run_due_jobs`, скрытый от агента. Данные —
Open-Meteo без ключа (`mcp/jobs/weather.ts`, инъектируемый `WeatherSource`), города из белого списка.
Тик дёргается по таймеру через `GET /jobs/tick`; мутирующие инструменты расписаний подчиняются тому
же гейту этапа задачи, что и внутренние мутации.

## Day 19 — пайплайн MCP-инструментов

Третий MCP-сервер `agent-mcp-research` пишет файлы-отчёты: `search` (Wikipedia ru через
инъектируемый `WebSource`), `summarize` (детерминированное экстрактивное сжатие без LLM),
`save_to_file` (`REPORTS_DIR`, санитайз имени) и проверочные `list_reports`/`read_report`.
Цепочку `search → summarize → save_to_file` автоматически ведёт обычный цикл агента: он передаёт
вывод предыдущего инструмента в аргументы следующего — отдельного движка пайплайна нет.
`save_to_file` изменяющий, поэтому цепочка целиком выполняется на этапе исполнения после
подтверждения, а `list_reports`/`read_report` — на этапе проверки. Тесты: адаптер/тулы
(`tests/mcp-research.test.ts`) и сама цепочка с передачей данных (`tests/mcp-chain.test.ts`).

## Day 20 — оркестрация нескольких MCP-серверов

Четвёртый MCP-сервер `agent-mcp-market` отдаёт курс валют (`exchange_rate { base?, quote?, date? }`,
дефолт EUR/USD, данные ЕЦБ/Frankfurter без ключа) — уже четвертый независимый сервер наряду с
`demo`/`jobs`/`research`. Агент комбинирует инструменты разных серверов в одном ходу: выбор тула и
порядок вызовов задают описания (с провенансом `[server]`), а длинный флоу
`db_overview`/`search`/`get_weather_report`/`exchange_rate` → `summarize` → `save_to_file` →
`list_reports` ведёт всё тот же цикл `decide→act`. Лимит действий на ход поднят до 10, чтобы хватало
на длинный флоу. Тест `tests/mcp-orchestration.test.ts` проверяет выбор и порядок вызовов сразу
четырёх серверов и передачу данных между ними.

Код агента и всех дней — в `src/`; агентская фича — в `src/features/agent/`.
