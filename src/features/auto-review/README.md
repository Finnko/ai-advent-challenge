# Авторевью студенческого проекта (Day 35)

Проверка проекта «Шесть городов» на защите: страница `/auto-review`, где проверяющий загружает
zip-архив, получает план проверки, запускает прогон и читает отчёт по критериям. Фича
dev/local-only и не зависит от `features/rag` и `features/agent` — только `@lib`.

## Как это работает

```
zip → распаковка → npm install → дев-сервер ─┬─ Playwright (Chromium + Firefox) → Б1 / Б2 / Б3
                                             └─ исходники ─┬─ статические правила → Д2, Д9, Д11, Д19, Д21, Д24, Д28
                                                           └─ модель (DeepSeek) → остальные Д и формулировки замечаний
                                             → сборка отчёта → validation → done
```

Обе дорожки идут параллельно: статические проверки и оценка моделью не требуют дев-сервера и
стартуют сразу после распаковки. Если проект не устанавливается или не стартует, базовые критерии
получают `not_checked` с причиной («проект не запускается»), а критерии по коду всё равно считаются.

Источник проекта — zip-архив **или** путь к уже распакованной папке (в UI переключатель
«zip-архив / папка на диске», в CLI `--dir`). Ключ проекта выводится из имени выбранного архива или
папки (`domain/project-key.ts`: без `.zip`, с транслитерацией кириллицы); в UI его можно поправить, в
CLI — переопределить через `--key`. Внешнюю папку сервис не удаляет при очистке исходников:
удаляются только собственные копии, а связь с ней просто снимается.

## Критерии

- **Б1** — все обязательные сценарии ТЗ пройдены (Chromium).
- **Б2** — при выполнении обязательных сценариев нет необработанных ошибок (сетевые ошибки не считаются).
- **Б3** — те же сценарии зелёные во всех проверяемых браузерах.
- **Д** — дополнительные критерии защиты. Часть считается детерминированно и передаётся модели как
  факты, остальные оценивает модель по чанкам кода.

Статус критерия — `pass | fail | not_checked`. Модель не переключает `pass/fail` у Б1–Б3: она
формулирует причину из сырых результатов прогона. Замечания — маркированные строки в деловом тоне
(«следует …», «надо исправить …»), только по непройденным критериям.

## Задача

Ведётся через `@lib/task-state`: `planning` (проект получен, план собран из критериев, ждём
подтверждения) → `execution` (параллельные дорожки) → `validation` (проверяем, что у каждого
критерия есть вердикт) → `done`. Кнопка «Утвердить план» запускает прогон.

Повторная проверка: тот же проект приходит с исправлениями новым архивом с `resumedFrom` — план
строится только из ранее проваленных пунктов, не затронутые критерии переносятся из первичной
проверки.

Прерывание: кнопка «Прервать проверку» (до запуска — «Отменить проверку») переводит Задачу в
`cancelled`, статус проверки — `cancelled`, а текущий дочерний процесс (`npm install`, дев-сервер,
Playwright) убивается вместе с группой процессов через `AbortController`. Прерванная проверка не
считается ни успешной, ни проваленной: отчёт по ней неполный. CLI отменяет проверку и по Ctrl+C, и
по истечении общего дедлайна `AUTO_REVIEW_RUN_TIMEOUT_MS` (по умолчанию 30 минут), так что прогон не
остаётся висеть в статусе `running`.

Экран проверки: вердикт сверху (сколько пунктов пройдено, полоса pass/fail/not_checked и коды
провалов), ниже — ведомость критериев по секциям с фильтрами «Все / Провалы / Не проверено»,
справа — этапы и сворачиваемый лог. Отчёт целиком, только замечания и каждый отдельный пункт
копируются в Markdown одной иконкой (буфер — `domain/markdown.ts`); «Прошлые проверки» и «Исходники
проекта» (удаление загруженных копий или «забыть папку на диске», с опцией стереть историю) — ниже.

## Модули

- `data/criteria.ts` — список Б1–Б3 и Д с правилами и способом оценки (`playwright | static | model`).
- `data/spec-map.ts` — соответствие spec-файлов пунктам ТЗ и критериям.
- `domain/code-checks.ts` — детерминированные Д-правила по исходникам.
- `domain/playwright.ts` — разбор отчёта прогона и подсчёт Б1/Б2/Б3.
- `domain/assemble.ts` — сборка итоговых вердиктов из трёх источников.
- `domain/contract.ts`, `domain/findings.ts` — контракт ответа модели и нормализация замечаний.
- `domain/prompt.ts` — промпты и упаковка кода в бюджет токенов.
- `server/pipeline.server.ts` — оркестратор прогона и дорожек.
- `server/project.server.ts`, `server/exec.server.ts` — распаковка, `npm install`, дев-сервер, таймауты.
- `server/playwright.server.ts` — запуск набора из челленджа против дев-сервера студента.
- `server/sources.server.ts`, `server/judge.server.ts`, `server/llm.server.ts` — исходники, модель, DeepSeek.
- `server/db.server.ts`, `server/store.server.ts` — `node:sqlite` (`auto-review.sqlite`): `projects`, `reviews`, `runs`.
- `server/service.server.ts`, `server/registry.server.ts` — публичный API и отсоединённый прогон.
- `functions/`, `api/` — сервер-функции и react-query хуки (прогресс — поллинг `runs`).
- `components/`, `pages/` — консоль проверяющего: список проектов, экран проверки, отчёт, лог, история.
- `cli/auto-review.ts` — `npm run auto-review -- --zip <path> [--key <key>] [--resume <id>]`.
- `e2e/` — Playwright-набор по ТЗ (не исполняется Vitest, см. `vitest.config.ts`).

## Запуск

```bash
npx playwright install chromium firefox   # браузеры набора (или npm run playwright:install)
npm run dev                               # страница /auto-review
npm run auto-review -- --zip ./ivan-ivanov.zip                     # ключ: ivan-ivanov
npm run auto-review -- --dir ./student-project --key ivan-ivanov   # уже распакованный проект
```

Env: `AUTO_REVIEW_DB_PATH`, `AUTO_REVIEW_MAX_UPLOAD_BYTES`, `AUTO_REVIEW_INSTALL_TIMEOUT_MS`,
`AUTO_REVIEW_SERVE_TIMEOUT_MS`, `AUTO_REVIEW_TEST_TIMEOUT_MS`, `AUTO_REVIEW_RUN_TIMEOUT_MS`,
`AUTO_REVIEW_CODE_BUDGET`, `AUTO_REVIEW_JUDGE_MAX_TOKENS`, `AUTO_REVIEW_BROWSERS`. Модель — DeepSeek
(`DEEPSEEK_API_KEY`, `DEEPSEEK_MODEL`).
